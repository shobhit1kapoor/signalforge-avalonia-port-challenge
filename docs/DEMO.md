# Runtime demo and screenshot evidence

The repository retains before/after, simulator, migration-tab, Dock workspace, floating-window and interactive PTY screenshots, plus actual pass/fail protocol-test reports. All 261 tests pass in the CI-equivalent split on Windows and Ubuntu 26.04 under WSL2: 260 tests with `Terminal2SendWorkflowViewModelTests` excluded, then that workflow test separately. The combined Windows invocation exceeds the 3-minute hang limit at the dispatcher workflow; the combined Linux invocation fails with an Avalonia dispatcher thread-ownership exception. No hosted CI run has happened. These results do not establish hardware operation, native macOS, bare-metal Linux, or every interactive workflow. The loopback Terminal2 LRC pass/fail path now reassembles fragmented RX chunks before validation; the retained Modbus simulator screenshots predate the current protocol-test fault selector and compact live-state layout. Text-file transfer and Dock drag-re-dock/custom-layout restore have not been manually verified.

## Retained protocol-test reports

- [`modbus-register-read-pass.json`](evidence/modbus-register-read-pass.json) is the exported passing loopback read. It contains the scenario, both passing steps, exact TX/RX hex and Base64 bytes, the simulator endpoint, and `TEST #1` event-sequence references.
- [`modbus-register-read-fail.json`](evidence/modbus-register-read-fail.json) is the exported controlled failure with **Corrupt Modbus function code on response 1**. The send step passes; the Modbus assertion fails because the response function is `0x02` instead of `0x03`. The exact response bytes and `TEST #2` event-sequence references are retained.

Captures use their recorded native window sizes; they are not all resolution-matched. Simulator screens contain real traffic to an ephemeral loopback-only TCP server; the fixtures are explicitly labeled simulated. They are not captures from a physical device. The retained byte-count-corruption screenshot and trace change the Modbus TCP byte-count from `04` to `05`; that earlier simulator demo is separate from the current protocol-test fault plan, which changes the response function code. Modbus TCP has no frame checksum. The recorded request is `00 01 00 00 00 06 01 03 00 00 00 02`; the good response is `00 01 00 00 00 07 01 03 04 12 34 BE EF`.

Terminal2 was built from the pinned checkout for this local screenshot because the host did not have the .NET Framework 4.8 Developer Pack. The build used temporary reference/resource assemblies and build properties; no Terminal2 source/project files were changed. It ran with an isolated temporary `LOCALAPPDATA` profile directory. The regular SIGNALFORGE build does not depend on those temporary settings.

## Repeat the simulator demo

1. Run `dotnet run --project src/SignalForge.Desktop`.
2. Open **TEST**, keep **Local Modbus simulator** selected, and keep the fault plan at **None**. Run the built-in Modbus read example; both steps should pass, with exact request and response bytes in the results.
3. Select **Corrupt Modbus function code on response 1** and run the example again. The send step passes and the assertion fails with the expected and observed function codes; the changed response bytes remain visible. The UI explains that Modbus TCP has no checksum.
4. Select **LOAD STX/LRC EXAMPLE**. It chooses the loopback-only Terminal2 simulator and creates a request/expected response with a valid STX/ETX/DLE/LRC frame. With the fault plan at **None**, run it; both the byte comparison and explicit **Validate Terminal2 LRC** assertion pass, and TX/RX evidence plus assertions appear in the timeline.
5. Select **Corrupt Terminal2 LRC on response 1** and run again. The byte comparison and LRC assertion fail; the exact received frame remains visible and the decoder reports `stxetx.bad-lrc` with expected and observed LRC values. The simulator only binds to loopback and closes after the test.
6. Set a writable `.json` report path and export a run to retain a versioned report with scenario settings and byte evidence. The two reports linked above were exported from the desktop app. Each event row in Device Explorer is drawn from the same recent trace activity and selecting it selects the event in the main timeline/inspector. Use the main byte-session trace controls to save, replay and compare JSONL traces from a captured session.

The profile fixture was generated by the pinned Terminal2 source, then only its local log path and export timestamp were sanitized. The Core acceptance test imports, exports and re-imports it. The desktop migration tab also imports the same fixture and exports a `.profile`; the fixture has no populated macros, so macro execution still requires a user profile with real macro content.

## Other workstation flows

- **Command palette:** click **COMMANDS** or press Ctrl+Shift+P (⌘+Shift+P on macOS), then search for a workspace or transport action. Actions reflect current command availability and open their existing feature views.
- **Remote terminal:** open **REMOTE SHELL · SSH/TELNET**, select SSH or Telnet, enter the endpoint, and connect. SSH accepts a password for that process session and validates the host with the local OpenSSH `known_hosts` file or a supplied SHA-256 fingerprint. Telnet is unencrypted. These terminal sessions are separate from byte-session capture; no remote endpoint has been used for verification.
- **Terminal2 filters and receive history:** open **TERMINAL2 FILTERS** to edit up to 12 first-match rules and optionally associate an exact macro title. A matching completed live RX line runs the macro in that first matching filter; pending triggers are serialized through a 64-item queue, and historical traces never trigger macros. Open **RX LINE HISTORY** to inspect complete received lines reconstructed across arbitrary chunks, search backward/forward, stop at a matching line, or freeze/resume the display while recording continues. The partial line and exact line hex are shown separately; CR, LF and CRLF endings are labeled. Matches color complete lines and RX timeline rows without changing trace bytes.
- **Staged profile connection:** importing a supported Terminal2 profile displays the serial/TCP values staged for the next byte-session connection. It does not alter a connection that is already active.
- **Text-file transfer:** open **TEXT FILE TRANSFER**, choose a text file, select whether to append CR and/or LF, and set the delay between nonempty lines (0–10,000 ms). Start the transfer, then pause/resume or cancel it as needed; the screen reports line progress and transfer status. Core behavior and tests cover CR/LF splitting, UTF-8 text, `$HH`/`$$` escapes, appended line endings and cancellation. Desktop runtime behavior is not part of the current verification record.
- **XMODEM:** open **XMODEM** with a connected serial port and enter an input path, NAK retry limit and ACK timeout. Start the receiver on the remote device first, then begin the send. The tab reports acknowledged blocks/bytes and errors; the trace records protocol bytes. Core tests cover packet framing, CRC, retries, timeouts, cancellation and EOT. No physical serial transfer has been run.
- **Workspace layout:** drag the splitters to resize the explorer, inspector and timeline panes. The desktop stores Dock settings at `%LOCALAPPDATA%\SignalForge\Settings\dock-workspace.json`; the current Windows workspace is shown in the retained Dock screenshot. **Float** opens Protocol Studio as a separate native window, and **RESET LAYOUT** closes that float and restores the default workspace. Dragging a float back into the main window and restoring a custom layout after application restart have not been manually verified.
- **Local PTY:** open the **LOCAL SHELL** feature tab. On Windows, the selected tab starts PowerShell on demand; a prompt and command output were observed in the current build. The PTY is independent of byte-session transport and trace capture.
- **Profile library:** startup creates Terminal2's `Default` profile if needed and restores selection from the collection's active marker. Create another blank Terminal2-default profile or import a `.profile` in the migration tab, then open **PROFILE LIBRARY** to save, search, copy, load, rename or delete profiles. Select a profile to edit serialized connection, send, display, font/color and logging settings; Save writes a detached draft and does not replace the active workspace profile. `Active` and `ShowLogControl` lack serializer keys. Copy and create refuse to replace existing files. It uses the local application-data folder `SignalForge/Terminal2Profiles` and validates names before file operations.
- **Terminal2 traffic logging:** after importing a profile and connecting, use **START LOG** in the workspace toolbar or run a macro containing `#STARTLOG` and `#STOPLOG`. The traffic log records timestamped TX/RX hex using the active profile's log directory, prefix and maximum size. Missing directories are reported. The automatic JSONL session trace continues regardless of this switch.
- **Macro editor and hotkeys:** open **MACRO EDITOR** after importing a profile. Select any of the 192 slots across four banks, edit its title/text and timing/repeat/CR/LF options, then apply the change to the loaded profile. Choose the active hotkey bank; F1–F12 run the first row, and Shift/Ctrl/Alt+F1–F12 run rows two through four. The hotkeys are active in the main window and Terminal2 send-text field; other text controls retain their keys. Empty slots and disconnected sessions report status without sending. Save the changed profile in **PROFILE LIBRARY** or export it from **TERMINAL2 MIGRATION**.
- **User schema studio:** open **USER SCHEMAS**. The built-in example defines an eight-byte telemetry packet with an `A5 5A` signature and typed fields. Enter the matching sample bytes and decode to see `VERIFIED`, field ranges and values. The reusable JSON form is in [`examples/telemetry-schema.json`](examples/telemetry-schema.json). Schema files are loaded and saved by entering a path.
- **Trace replay:** load `docs/evidence/modbus-good-loopback.jsonl` from the timeline controls and replay it. Pause and resume RX playback; seeking requires pause and takes a trace sequence from the timeline. Replay preserves the TX verification cursor when seeking, blocks an RX event until earlier recorded TX is verified, and rejects TX that crosses a recorded RX boundary. RX timing is scaled by replay speed; TX timing follows the application. Replay completion reports expected TX bytes that the application did not send.
- **Binary X-Ray:** select a byte event in the main timeline. The inspector presents 16-byte rows with offsets and printable ASCII, alongside the selected protocol decoder output. Large payload display is bounded; saved traces retain all bytes. Open **BINARY TOOLS** to search the selected event by hex pattern, preview a replacement on a copy, or convert bytes to and from Base64. These operations do not modify the trace.
- **Paired trace comparison:** open **TRACE COMPARE** and use `docs/evidence/modbus-good-loopback.jsonl` as the expected trace and `docs/evidence/modbus-corrupted-loopback.jsonl` as the actual trace. Signature anchors and bounded local matching align observations with missing, extra, or reordered rows. Expected and actual rows share a relative-time origin; the comparison reports event, direction, payload-byte and relative-timing differences, quantifies relative delay and presents evidence assessments while leaving root cause uncertain. Selecting a difference opens its source trace and sequence in the main timeline.
- **Protocol test engine:** open **TEST**, select a local loopback simulator, and run the built-in Modbus read example with no fault. Confirm both steps pass and inspect the exact request/response evidence. Select **Corrupt Modbus function code on response 1** and run again: the send step passes, the Modbus assertion fails with the observed and expected function codes, and the changed response remains visible as exact bytes. This is a protocol-field mismatch; Modbus TCP does not have a checksum. Then select **LOAD STX/LRC EXAMPLE**, run with no fault, and repeat with **Corrupt Terminal2 LRC on response 1**. The LRC validator explicitly reports `stxetx.bad-lrc` on the corrupted response. Both simulator runs add their TX/RX evidence and assertions to the trace timeline. Set a writable `.json` report path and export either run as a versioned report with its result and byte evidence.
- **Terminal2 send workflow:** import the sanitized Terminal2 profile fixture in **T2 SEND**. Select a completed line in **RX LINES** to recall its display text into the command editor; this does not send it. Send-as-you-type follows the profile preference and shows an irreversible-send status; incomplete `$HH` and `$$` escapes wait for completion. The **STX/ETX** button sends the encoded frame with profile CR/LF outside the frame. Automated loopback view-model tests verify the exact transmit bytes and that macro execution pauses typing.
